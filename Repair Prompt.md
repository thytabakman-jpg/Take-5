# Repair Skill: Comprehensive PD Semantic Audit and Repair

## 1. Governing objective

Improve the substantive quality, semantic precision, logical integrity and functional effectiveness of every targeted document, according to its purpose.

The tools are instruments for accomplishing this objective. Successful tool execution alone does not constitute meaningful research improvement. Prioritize discovering problems, developing solutions, implementing validated repairs and verifying improvements.

## 2. Target documents

The user specifies the target documents when invoking the Repair skill. Targets may include individual files, multiple files, folders or combinations thereof.

Identify and verify the exact repository, folder paths and files included in the requested execution scope.

If the target documents are unambiguous, proceed directly. If the scope is ambiguous, obtain clarification before execution.

Process the target documents individually, following any execution order specified by the user.

Do not modify documents outside the established execution scope.

## 4. Document semantic preflight

Apply the Semantic Preflight Protocol's every-word rule to the entire file, rather than merely its controlling question.

The original protocol is a provisional prompt-intake protocol. This document-wide application is an authorized adaptation, not an already certified native execution profile.

Examine every word, phrase, sentence, paragraph, heading, table, quotation, mathematical expression and analytical conclusion.

Classify non-load-bearing language without generating unnecessary commentary. Concentrate investigative and analytical effort on language that materially affects meaning, reasoning, evidence or document functionality.

Identify and supply the result-sensitive semantic coordinates required by PDAudit, including:

- Object identity.
- Definitions.
- Predicates.
- Quantifiers.
- Modality.
- Temporal conditions.
- Scope and domain.
- Referents.
- Logical relations.
- Necessary and sufficient conditions.
- Explicit and implicit premises.
- Presuppositions.
- Ambiguities.
- Attribution.
- Source interpretation.
- Evidentiary strength.
- Inferential strength.
- Qualifications and exceptions.
- Claim-type classification.
- Historical versus current formulations.
- Terminological consistency.
- Redundancy and omitted distinctions.

Apply the mandatory mathematical object-integrity and prerequisite-integrity gates specified in the PDAudit governing protocol wherever formal or mathematical reasoning appears.

## 5. Document-specific requirements

Evaluate each document according to its purpose, content and function.

Use GOAL to evaluate its purpose, governing questions and objectives.

Use Architecture to evaluate its structural organization, heading hierarchy, section responsibilities and dependencies.

Use PDAudit, ASSERT and other applicable tools to evaluate its semantic precision, claims, evidence, reasoning and conclusions.

Ensure that:

1. Established, historical, reconstructed and exploratory claims remain distinguishable.
2. Cited sources support their attributed claims.
3. Conclusions follow from the available evidence.
4. Qualifications are preserved throughout the document.
5. Superseded formulations cannot contaminate current conclusions.
6. Analysis, significance and substantive contributions are defensible.
7. Discoveries are not confused with unsupported originality claims.
8. Material evidence, objections and unresolved questions are preserved.
9. The underlying Markdown or other document syntax correctly implements the intended structural hierarchy and formatting.
10. All internal and external links resolve correctly, including file paths, URLs and section anchors.
11. Each link leads to its intended, relevant and current destination.
12. Links passing through obsolete placeholders, redundant redirects or unnecessary intermediary documents are replaced with direct links to their intended destinations.
13. Links to functional inventories, indexes, navigation hubs and other intermediary documents are preserved wherever those documents serve a substantive purpose.

Where source evidence is insufficient, investigate the relevant external sources rather than manufacture a resolution.

## 7. Autonomous repair cycle

Complete the following cycle for each individual file before proceeding to the next.

1. Retrieve and freeze the current file version.
2. Read the entire document.
3. Conduct the comprehensive semantic preflight.
4. Execute the mandatory and applicable conditional tools.
5. Consolidate discoveries and eliminate duplicate findings and false positives.
6. Investigate unresolved substantive problems using the applicable tools and external evidence.
7. Develop concrete textual and analytical repairs.
8. Assess each proposed repair using GO / NO-GO / TWEAK.
9. Refine TWEAK recommendations through applicable recursive tool execution.
10. Reject NO-GO recommendations.
11. Implement validated GO recommendations directly in GitHub when operating in repair mode.
12. Retrieve the modified document and verify the actual changes.
13. Re-examine affected passages and downstream dependencies for regressions, using TRC to manage applicable consequences and verification obligations.
14. Record any remaining material limitations.
15. Proceed immediately to the next file.

Use genuinely independent evaluation where available. If that capability is unavailable, distinguish same-context adversarial review from independent assessment and do not falsely claim the latter.

I authorize individual file repairs without requiring further approval when operating in repair mode.

Preserve substantive research, source evidence, objections, useful exploratory material and structural and operational functionality. Research repositories are not condensed manuscript drafts.

When the user explicitly requests recommendations without implementation, complete the applicable analysis and repair development stages, present the proposed repairs and their supporting rationale, and leave the target documents unchanged.

## 8. Sequential execution and continuation

Work on one file at a time.

Finish and verify each file before beginning the next. In repair mode, commit all implemented repairs individually. Where no material defect is identified, verify completion without modifying the file.

Do not stop after each file to request permission. Continue autonomously across all the files within the authorized execution mode.

Maintain a compact continuation record containing completed file identifiers, verified commits where applicable, material findings, repairs or recommendations, unresolved issues and the next file.

If interrupted by execution limits, resume from the first unfinished file using the current repository state.

## 9. Success criteria

Measure success primarily through:

- Substantive defects resolved.
- Logical and semantic precision improved.
- Evidence and attribution strengthened.
- Invalid inferences corrected.
- Valuable research discoveries established.
- Philosophical contributions improved, where applicable.
- Existing research preserved.
- Structural and operational functionality preserved.
- Document-specific responsibilities fulfilled more effectively.
- Repairs implemented and verified, or validated recommendations produced in recommendations-only mode.

The number of tools executed is secondary.

A file that contains no material defect does not require an artificial edit.

## 10. Reporting

Provide concise progress reports identifying the actual problems discovered and repairs implemented or recommended.

At completion, report:

- Files completed.
- Substantive problems discovered.
- Severity of those problems.
- Repairs implemented or recommended.
- Rationale for each material repair or recommendation.
- Verified GitHub commits, where applicable.
- New research discoveries.
- Remaining unresolved issues.
- Any incomplete tool or verification requirements.

Distinguish completed work from partial execution.

**Begin with the first file immediately. Complete its full analysis and authorized repair or recommendation cycle, then proceed directly to the next file and continue in order until all targeted files have been processed. Do not substitute a plan for execution.**
