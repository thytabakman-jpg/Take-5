## Recovered purpose

Take-5 is not merely a successor repository and not merely a tool collection.

Its intended role is the canonical operating system for a cumulative autonomous
research/improvement process.

The target behavior is:

Input or admitted state
-> recover current object, authority, provenance, and goal
-> discover justified work, including work not explicitly listed by the user
-> generate/select applicable capabilities
-> bind and execute real tools/workers
-> admit and reconcile results
-> verify protected behavior
-> propagate material consequences
-> persist durable current state and history
-> regenerate the work frontier
-> automatically reenter at the earliest invalidated dependency
-> stop only at relative closure or typed OPEN/BLOCKED/CONFLICT.

## System decomposition

The target system has five layers.

### L0 Kernel

The kernel is small and privileged.

It owns:
- typed identity;
- authority;
- provenance;
- legal state transition;
- evidence/admission boundary;
- OPEN/BLOCKED/CONFLICT preservation;
- execution truth;
- durable transition/event receipt;
- reentry trigger semantics.

The kernel does not own every useful tool, research method, planning strategy, or
domain worker.

### L1 Durable research state

State is not one mutable blob.

It separates:
- current derived state;
- append-only event/execution history;
- admitted claims/evidence;
- work ledger;
- capability/tool currentness;
- failure/no-gain memory;
- dependency/currentness graph;
- OPEN/BLOCKED/CONFLICT frontier.

A current state must be reconstructible from durable evidence/history.

### L2 Work and controller layer

The Endogenous Work Generator owns discovery/regeneration of justified work.

ImprovementCore owns adaptive policy:
- observe;
- recover/freeze object and goal;
- generate questions/work candidates;
- select capability package;
- route external acquisition when higher-value;
- delegate;
- execute;
- admit/reconcile;
- learn from gain/no-gain/failure;
- invalidate stale plans;
- reselect/reenter.

ImprovementCore is not the whole system.

### L3 Capability/runtime layer

Capabilities are behavior-first and separately bound to actual runtime adapters.

The system distinguishes:
AVAILABLE
-> ELIGIBLE
-> SELECTED
-> BOUND
-> EXECUTED
-> RESULT_USED
-> VERIFIED.

A named capability with no executable binding does not count as execution.

Outside capabilities are first-class:
- connected/private sources;
- repository research;
- web search;
- external tools/connectors.

Unavailable materially required outside capabilities leave a typed OPEN gap rather
than forcing internal reconstruction.

### L4 Continuity/interface layer

Jane is the direct continuity supervisor/facade, not the primary solver.

Jane owns:
- entry-state reconstruction;
- canonical bootstrap;
- currentness/provenance continuity;
- question/frontier supervision;
- capability visibility;
- delegation packaging;
- anti-loss receipts/maps;
- admitted-delta synchronization;
- discovery-to-work continuity;
- concise faithful user-facing projection.

ImprovementCore remains the adaptive controller.

## Closure

A bounded run ending is not completion.

Relative closure requires:

1. no live justified work remains under the declared basis;
2. all selected/executed work has terminal receipts;
3. every material result is admitted, rejected, or typed OPEN/BLOCKED/CONFLICT;
4. current state is reconstructible from history;
5. affected dependents have been propagated;
6. currentness checks pass;
7. no live reentry trigger remains.

## Anti-loss law

Every material discovery must end in one of:

- admitted current control;
- project-local state;
- research/provenance;
- evidence/history;
- verified duplicate;
- conflict;
- OPEN/BLOCKED.

No material discovery is allowed to exist only in chat text, an orphan audit, a
temporary tool output, or an unreferenced file.

## External architectural checks

The target remains consistent with three outside architecture lessons:

1. microkernel systems place only globally privileged mechanisms in the trusted core;
2. durable workflow systems distinguish orchestration/history from side-effecting workers;
3. modern agent runtimes separate orchestration, tools/handoffs, state, guardrails,
   and tracing rather than collapsing them into one agent/tool object.

These are comparators, not authority.

## North-star criterion

Take-5 reaches its intended end state when an ordinary user interaction can enter through
Jane/host, reconstruct the current system state, let the system discover and execute
justified work with real internal or outside capabilities, durably integrate verified
results, automatically continue/reselect after material deltas, and return only when
relative closure or an explicit typed gap is reached.

No repeated user instruction such as "run the next tool", "look in Research", "use the
internet", "propagate that result", or "continue" is required for a materially implied
continuation.
