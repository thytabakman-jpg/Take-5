# SOP for New Load-Bearing Projects and Formal Objects

Status CURRENT CANDIDATE
Date 2026-09-25

## Trigger

Use this SOP whenever a new project, controller, tool family, mathematical framework, architecture, or other load-bearing named object begins to influence work beyond one disposable local task.

## Step 1 Freeze the object

Identify exactly what is being created.

Do not begin with filenames or styling.

Record

- object identity
- job
- scope
- accepted mathematical or semantic baseline
- protected constraints
- completion predicate
- authority

## Step 2 Classify the required artifact roles

Start with the eight-role core.

1. Project Charter
2. Canonical Model
3. Presentation or Output Invariant
4. Artifact Registry
5. Currentness and Source Manifest
6. Friction and Gap Ledger
7. Validation Contract
8. Operating SOP

An artifact role may be marked NOT_APPLICABLE only with an explicit reason.

Do not collapse roles merely because one file can physically contain both.

## Step 3 Add supporting artifacts only when demanded by the object

Examples

- rendered assets
- machine-readable schemas
- tests and validators
- benchmark fixtures
- runtime implementations
- migration records
- authority records
- data or source manifests

Supporting artifacts implement or evidence a core role. They do not create a ninth core role by default.

## Step 4 Run the 36-cell architecture check

Evaluate the artifact system across

Scope

- SYSTEM
- SUBSYSTEM
- COMPONENT
- INTERFACE
- BOUNDARY
- CROSS_LAYER

Mode face

- EXPAND
- CONTRACT
- INWARD
- OUTWARD
- ISOLATE
- COUPLE

The check asks where information, currentness, validation, or ownership can be lost.

It does not require 36 separate artifacts.

## Step 5 Build the registry before producing volume

Every artifact receives

- stable artifact id
- role
- path
- authority
- status
- dependencies
- source lineage
- validation owner

The registry is created before large-scale production so later files cannot become anonymous governing objects.

## Step 6 Separate source from authority

Historical files, chat outputs, experiments, and candidates remain evidence until admitted.

Newer does not mean current.

Persisted does not mean authoritative.

Rendered does not mean mathematically accepted.

## Step 7 Validate by layer

Run semantic, artifact, rendering, and integration validation separately.

Do not use one passing layer as evidence for another.

## Step 8 Reenter after every material delta

A change to mathematics, identity, version, currentness, source lineage, renderer behavior, or project scope reopens the affected artifact set.

Use the registry dependency graph to determine the affected cone.

## Step 9 Close only relative to the declared basis

Closure language states the searched corpus and current artifact basis.

Undiscovered historical sources remain epistemically possible.

## Minimum artifact count

For a substantial load-bearing formal project, the default core count is eight artifact roles.

The physical file count can exceed eight because rendered assets, schemas, runtime implementations, and tests are supporting artifacts.

A smaller core is licensed only when one or more roles are formally NOT_APPLICABLE, not because they were forgotten.
