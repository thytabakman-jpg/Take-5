## 1. Emergent object extraction

The new object is not best represented as a spatial metaphor.

Candidate object:

BindingTopology = typed relation graph among
{Item, ToolOrProgram, HostOrController, State, View, CandidateUniverse, Result}.

Let

B = <N,E,tau>

where N is the participating node set, E directed relations, and tau types each relation.

Candidate relation types include:

- READS
- WRITES
- CONTAINS
- DELEGATES
- UPDATES
- SELECTS
- CONSTRAINS

The user's phrases are therefore hypotheses about different graph forms, not yet primitive
enumerated states.

## 2. Why the candidate is load-bearing

Existing Take-5 evidence already distinguishes several binding structures.

A. Reasoning with a capability's semantics is not equivalent to binding and delegating to it.

B. A passive item acted on by a tool is not equivalent to an admitted item/state delta that
changes views and the candidate universe through RCDL.

C. The same apparent behavior can move between tool and host/controller; Take-5 already requires
host-relative attribution for reduction and transfer claims.

D. ScopeEdge x Mode interactions are material, so an additional relation that changes local
control, feedback, or candidate reachability can be result-sensitive without becoming universal.

Therefore BindingTopology passes the load-bearing trigger for research admission.

## 5. The user's "item inside the tool" intuition

The intuition maps most closely to feedback-containing binding structures.

Static application:

Tool -> Item -> Result.

Representation-coupled embedding:

Item/Result
-> State/View
-> CandidateUniverse
-> Controller/ToolSelection
-> next Tool/Run
-> Item/State.

The second form lets the item change the machinery that will inspect it next.

That is the structural core of the Take-2 behavior already recovered by RCDL.

The new contribution of BindingTopology is to make the relation/ownership/feedback pattern itself
explicit and testable rather than leaving it distributed across host, delegation, mode and RCDL
semantics.
