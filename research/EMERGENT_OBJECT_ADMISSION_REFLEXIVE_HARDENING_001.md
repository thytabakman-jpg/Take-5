## Frozen goal

Make the future architecture automatically notice when its own reasoning introduces a new load-bearing concept, tool, stage, invariant, distinction, equation, controller, or architectural object; prevent that object from silently governing the system as unexamined prose; convert it into an explicit typed mathematical object; analyze/admit/reject it; integrate admitted consequences; and reenter the live job.

This is currently higher priority than hardening the existing tool set because it changes how all future discoveries enter the architecture.

## The deeper object

This is not merely ETH.

ETH is one instance of a more general problem:

EMERGENT LOAD-BEARING OBJECT ADMISSION.

Let a reasoning/execution step emit delta_t.

Define candidate extraction:

G_new(delta_t,S_t) -> P(O_new)

where O_new contains candidate newly introduced objects.

For candidate o, define load-bearing materiality relative to job J and continuation basis H:

LB_{J,H}(o,S_t) in {PASS,FAIL,OPEN}.

PASS means accepting, rejecting, changing, or removing o can change a protected future result, transition, interpretation, authority relation, verification obligation, architecture placement, routing decision, or completion claim.

OPEN cannot license silent integration.

## Proposed mandatory guard

For every material transition:

delta_t
-> DetectNewObject
-> TypeObject
-> AnalyzeObject
-> AdmissionDecision
-> IntegrateOrQuarantine
-> Verify
-> Reenter.

A new load-bearing object may not directly enter governing state.

Candidate invariant:

New(o) AND LoadBearing_{J,H}(o)
->
Admitted(o) OR Quarantined_OPEN(o).

No silent third state.

## Mathematicalization requirement

"Convert it to math" is not equivalent to forcing every object into an equation.

Mathematicalization means produce the minimum explicit formal object needed to expose result-sensitive structure:
- identity and scope;
- type/role;
- inputs/outputs;
- state dependence;
- relations/dependencies;
- invariants;
- partiality/OPEN;
- transition effect;
- authority;
- equivalence/reconstruction basis;
- stopping/completion condition where applicable.

Some objects will be predicates, relations, state coordinates, transition systems, graphs, algebras, partial functions, set-valued maps, contracts, or typed schemas rather than scalar equations.

## Candidate admission pipeline

1 DISCOVER
Detect semantic novelty/delta.

2 OBJECTIFY
Freeze candidate identity and distinguish it from renamed existing objects.

3 TYPE
Determine whether it is a distinction, predicate, relation, transform, generator, state, policy, controller, invariant, guard, interface, runtime binding, evidence object, or composite.

4 MATHEMATIZE
Construct the smallest explicit representation sufficient for result-sensitive analysis.

5 ATTACK
Use MTA by default on mathematical/tool structure.
Use PD/PDAudit when object identity/frame/sensitivity is uncertain.
Use Multi-Object when interaction/support residual is material.
Use Diagnosis when causal rivals affect intervention.
Use ARA when persistent/canonical realization is involved.
Use RTC only after the object/job is typed enough for same-job strict-gain search.

6 ADMIT
Return ACCEPT, REJECT, MERGE/SUBSUME, RIVAL, OPEN, or BLOCKED.
Admission is not promotion.

7 INTEGRATE
Update dependent architecture, maps, state, tests, ownership and provenance.

8 VERIFY
Check claimed effect and preservation.

9 REENTER
Recompute live frontier.

## Reflexive condition

The admission mechanism is itself a newly introduced load-bearing object.

Therefore it must pass through its own pipeline.

This creates a reflexive bootstrapping problem, not a license for infinite regress.

Let A be the admission transform.
A self-application sequence is:

A_0
-> A(A_0)
-> A(A_1)
-> ...

Reentry is required only when the previous pass produces a material delta under J,H.

Relative fixed point:
A_{n+1} approx_{J,H} A_n
and no reachable admitted challenge produces a protected material delta.

Failure to prove global fixed point yields typed OPEN, not endless mandatory recursion.

Strong candidate kernel-level contract:

No newly introduced load-bearing governing object may affect legal continuation until it has a typed identity and an admission disposition.

Formally:

Governs(o,S_{t+1})
->
KnownIdentity(o)
AND Typed(o)
AND Admission(o) in {ACCEPT,MERGE/RIVAL-with-explicit-policy}
