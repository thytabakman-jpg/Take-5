# Compile mathematics

## Objective and identity
Compile is a methodology, not a monolithic mathematical tool. Minimize unnecessary file count, informational redundancy and responsibility overlap subject to preservation of distinct protected material, attribution, logical integrity, functional responsibilities and dependencies. Optimization is a constrained reviewer decision, not a numerical global-optimum certificate. Three independent finite operators perform bounded computational jobs; the host owns semantic judgments.

## Common representation
A snapshot is a complete admitted map from repository-qualified file IDs `owner/repo:path/to/file.md` to UTF-8 text, plus independently recorded Git revision(s). SHA-256 of the JSON array of lexically sorted [ID,text] pairs binds operator inputs. Source spans use JavaScript UTF-16 code-unit offsets, half-open [start,end). Binary files, external repositories and unscanned scope are not silently certified.

## D: decompiler
For each admitted source, a deterministic structural partition U=(u1,...,uk) satisfies concat(U)=source text, preserving original occurrence, source, offsets, kind and historical flag. Historical revisions enter as separately identified exact texts. An explicit target set permits decomposition of selected files only while the full dependency snapshot remains digest-bound. Unchanged non-target files need no semantic decomposition. Each unit ID is SHA-256 of [source,start,end,historical]. Exact content grouping uses literal equality within structural kind. Candidate semantic overlap is Jaccard similarity |A intersection B|/|A union B| on case-folded Unicode alphanumeric token sets. A finite pair budget bounds work; incomplete comparison is explicitly reported. Similarity is never equivalence. The host classifies actual information types, assigns ownership, and decides semantic equivalence/subsumption under common scope, preserving provenance. The structural units may contain multiple semantic objects and are not automatically truth-apt.

## R: dependency transformation
Let V be admitted repository/file/section IDs and E the supported references extracted from text. A direct many-to-one file map M and explicit section map H induce the target mapping: H takes priority for referenced anchors; otherwise M applies to file targets, with explicit anchor mapping required for moved anchored targets. A reference in source s is rebased relative to M(s) or written as a cross-repository GitHub URL. Preparation computes rewritten original texts BEFORE the host merges them; audit extracts references from proposed final texts and checks every previously admitted target relationship remains represented. Multiple duplicate occurrences may collapse to one edge. Audit checks retired paths and candidate anchors, newly introduced unresolved internal references, and emits conservative literal residuals. A benign residual can be reviewed only with its exact source ID, retired target ID, candidate text digest and rationale; a reviewed literal never waives an actual dangling supported link. Supported parser scope: common inline Markdown links, reference definitions, quoted HTML href/src and unpinned main-branch GitHub URLs; ATX headings and explicit HTML anchors. This is not a complete Markdown parser or GitHub slug emulator. Unsupported constructs, branch-pinned URLs, dynamic imports, code/config references, comments, external targets and repository scope require separate review. No automatic code/config rewrite is licensed. Many-to-one file mappings are supported; split files or intentionally removed relationships need an explicit separately reviewed transformation, not a false pass.

## V: verification
For every nonseparator original unit (including admitted history), retain a trace to exact candidate span, a reviewed semantic representation, authorized removal, or reviewed immutable historical witness. Exact verification requires literal equality. When no explicit disposition exists, a unique exact occurrence in the same surviving file or its declared survivor generates an automatic span receipt. Non-target collateral files may avoid decomposition only if their complete candidate text exactly matches the dependency preparation output. Neither shortcut establishes semantic identity across contexts; the host reviews attribution and scope. Semantic review is recorded separately, not computational proof. Source partition coverage and identities are rechecked. Retirement requires absence of all authorized retired IDs and no unauthorized deletion; every edit/addition requires authorization. A dependency audit bound to exact snapshots plus independently evidenced scope/unsupported-reference review is required. Publication check compares independently retrieved published text against the candidate and records commit identity. This verifies admitted snapshots and declared mappings, not universal semantic or operational equivalence.

## Discovery, working views and history
Discovery mode constructs exact file groups (hash then literal equality), token posting lists, budgeted candidate pairs, Jaccard informational similarity, directional token containment and optional role/dependency Jaccard values. The weighted mean uses weights 6/2/2 only over available dimensions; missing dimensions remain null. Candidate clusters are graph connected components, not equivalence classes. Common tokens above the posting limit and exhausted pair budgets explicitly mark comparison incomplete. Residual counts are lexical indicators, not substantive residual proofs.

Decomposition emits a reversible structural registry plus optional readable consolidated and layered working views. Only the original source spans and registry are authoritative for exact reconstruction. Configurable textual indicators suggest multilabel semantic categories; unclassified units are unresolved. Layer comparisons filter the bounded comparison output; they are neither exhaustive nor semantic proof. Historical records may carry file and integer order coordinates; adjacent revisions and current admitted file are compared by exact unit-text membership, and historical units absent from current selected material are flagged. No network retrieval occurs in operators.

## Reusable reference index and relationship dispositions
The index records each supported reference occurrence, source offsets, kind, raw destination, parsed target and anchor, SHA-256 identity, and incoming/outgoing adjacency. Index mode emits reachability for requested roots. Preparation and audit may reuse actual version-1 operator output for content-identical records, checking source digests, edge digest, parsed targets, reference identities and literal spans; changed records are reparsed. Cache integrity checks are not a proof of extraction completeness: use only receipts from the same verified operator version, and perform final independent audit without an externally supplied index. Cache reuse does not eliminate snapshot hashing or residual scanning. Index mode emits the full index; preparation and audit omit its duplicate payload by default (includeIndex:true explicitly returns it).

Missing affected relationships may be admitted only through reviewed, authorized dispositions bound to edge ID, both snapshot digests and mapping digest. Internalise is limited to a formerly cross-file unanchored relationship whose mapped source and target coincide; subsumed requires an observed replacement destination; eliminate requires explicit nonoperative judgment. Unchanged relationships are not silently waived. Actual dangling links and anchor failures remain OPEN. The host establishes semantic/operational legitimacy and source-located evidence; a review flag is not a proof.

Typed inventory mode supports explicitly declared JSON object schemas with an entry array, repository-qualified path field and entry count field. Rewrite declared paths, deduplicate only identical full records after mapping, preserve all distinct metadata, recompute entry count and compare exact candidate output and target existence. Unsupported or stale schemas remain OPEN; arbitrary Markdown tables, custom manifests and live graph updates require their actual format-specific controls. The verifier may admit an undecomposed collateral inventory edit only with a matching actual inventory audit receipt and authorization.

## Provenance and benchmarking
The verifier returns a provenance manifest with frozen source identities, supplied repository revisions, source spans, accepted dispositions, mechanical edits and relationship reviews. Production verification uses requireProvenance=true and independently resolved sourceRevisions; after publication require independently retrieved exact manifest text and a durable reference. Keep receipts in an authorized surviving record or durable compilation ledger, not an unapproved new document. Manifest verification does not authenticate the host's storage locator or semantic judgments. Inventory reports, when supplied, must match the admitted before/after snapshots, mappings and output digests.

Measure elapsed time, connector requests and transferred bytes, repeated reads, operator work counters, host interventions and verified coverage on comparable real tasks; no measured speed claim follows from synthetic fixtures. Prefer actual observed baseline; PD is a simplicity reference rather than a same-job throughput baseline.

## Efficiency and execution
Three tools use only Node.js standard library at the CLI boundary. No general Take-5 runtime, mandatory tool battery, external model, API key or paid runner. Reuse snapshots and prepared edits. Host performs classification, layering, semantic deduplication, synthesis, architecture and functional review. Stop or retain source material when coverage or dependencies remain OPEN. No tool mutates repository files or publishes commits.

## Execution contract

This contract is normative for the [Compile Prompt](Compile%20Prompt.md). It owns technical invocation, coverage and verification requirements, not a competing execution sequence. Use the prompt's twelve numbered steps as the sole ordering. Each step consumes the previous step's actual output; a failed gate blocks only dependent work. Retain provisional source context until final assignments and dependency transformations are complete.

### Scope and preflight

Verify repository identities, branches, commit SHAs and authorized targets. Distinguish candidate discovery from permission to delete. Inventory all potentially affected repositories, files, references, history and functional entry points. Record binary/unavailable/unsupported content and scope gaps. Recommendations-only requests do not write. Never modify unrelated files. Freeze the exact source and dependency snapshot and record authorization for each proposed retired file and each affected write.

Resolve the goal, target, referents, requested operation, selectors, protected constraints, authority and success condition before acting. Distinguish candidate discovery, recommendations and execution. An explicit request to compile identified files authorizes validated consolidation and necessary, verified reference-only collateral edits within the established repository scope; it does not authorize unrelated improvements, uncertain retirements, or writes to additional repositories. Record the basis for each retirement and edit; obtain further authority only where genuinely absent. A folder is not blanket permission to delete every file. Preserve material ambiguity as OPEN and proceed with independent authorized work. Use the preflight principles in [Semantic Preflight Candidate](https://github.com/thytabakman-jpg/Reaserch/blob/main/Projects/Mathematics%20and%20Formal%20Methods/PD/protocol/PROMPT_SEMANTIC_PREFLIGHT_CANDIDATE.md) as design guidance, not as a promoted mandatory PD run.

For a discovery-only request, finish Step 1 without writing; for recommendations-only requests, complete applicable analysis and candidate verification without publication. No-write modes do not claim physical retirement. Use the user's approved scope and distinguish computational evidence from semantic review. Reapply affected checks when revisions, dependencies or mappings change.

Read the mathematics and inspect the exact tool input/output contracts. Cache verified bytes and successful fixture evidence for the same revision and execution environment. Do not retrieve unrelated Take-5 files.

Prefer Node.js 18+ with no third-party packages. Preserve the relative `runtime/` and `tests/` paths. Run:

```sh
node tests/test_compile.mjs
node runtime/compile_decompiler.mjs < decompile-input.json > decomposition.json
node runtime/compile_dependencies.mjs < dependency-input.json > dependency-report.json
node runtime/compile_verify.mjs < verifier-input.json > verification.json
```

Each operator consumes one JSON input and emits one JSON output. Retain exact input/output identities, tool revision, runtime, command or function, result and error status. Use the dependency executable for both preparation and audit; use the verifier again for publication. Do not infer a target-specific result from successful fixtures.

If an authenticated checkout is unavailable, retrieve the exact file bytes via the connected GitHub API at the frozen revision; use base64 or exact UTF-8 transport, verify Git blob SHA-1 (hash of `blob <byte-length>\0<bytes>`), and stage only the required files locally. If connector output is limited, use small batches and numbered base64 chunks; use [Connector-to-local source transfer helper](https://github.com/thytabakman-jpg/Take-5/blob/chatgpt-runtime-bootstrap/chatgpt-integration/connector_source_transfer.py) or equivalent local hash-checked transfer. [GitHub-only retrieval and recovery reference](https://github.com/thytabakman-jpg/Take-5/blob/chatgpt-runtime-bootstrap/chatgpt-integration/README.md#github-only-connector-to-local-transfer) provides recovery principles only; its full-runtime assembly, integration manifest, archive and regression obligations do not apply to these standalone operators. Do not route data through Google Drive, email or unrelated services, dispatch Actions runners or require an API key.

If the Node CLI is unavailable but an actual JavaScript execution environment can run the exact retrieved operator function bodies and all current fixture assertions without altering their computational logic, the direct-function route is admissible for these operators only. Verify source identity, record the exact extraction (omit only CLI/module import/export wrappers), run the complete fixture suite against those bodies, execute the real target JSON-equivalent inputs, and retain the actual results. Label this DIRECT_FUNCTION_EXECUTED, never NODE_CLI_VERIFIED. No hand-translated or simulated implementation qualifies. If source identity, complete fixture execution or actual target execution cannot be established, record the precise missing prerequisite as OPEN/BLOCKED. Continue independent authorized work without claiming computational completion.

### Step 1: Discovery

Use document purpose, responsibilities, informational overlap, history and dependencies. Exact duplicates are candidates, not automatically redundant files. Retain functional navigation or compatibility surfaces where genuinely needed. Defer final survivor paths and ownership to Step 8. Inspect material history; record immutable revision and source IDs.

Run C02 in discovery mode before selecting survivors: `{"mode":"discover","files":FILES,"targets":IDS,"metadata":{},"threshold":0.25,"maxPairs":50000,"maxPosting":250}` (replace placeholders with admitted JSON). Optional metadata per file supplies roles and dependencies arrays grounded in source evidence. Rank candidates, exact file groups and lexical residuals; flag skipped postings and budget limits, and review clusters rather than treating similarity or transitivity as equivalence. Return candidate groups, content/responsibility overlap, distinct information, historical residuals, relevant dependencies and proposed survivor(s). Classify groups as candidates, excluded or unresolved; discovery is not retirement clearance. Investigate material historical versions by exact Git revision and preserve useful evidence without indiscriminately copying superseded conclusions. 

### Steps 2–3: Consolidation and decomposition

Supply the complete admitted text snapshot as `{"files":{"owner/repo:path":"text"},"targets":["owner/repo:target.md"],"history":[{"id":"immutable source identity","text":"historical text"}],"maxPairs":50000,"threshold":0.7}`. Omit targets only for intentional whole-snapshot decomposition. Select all files being substantively changed or retired, not every unchanged dependency file. Run Decompiler. Keep the raw source occurrences, exact groups, candidate overlaps, and source spans. Do not interpret truncated candidate comparisons as exhaustive. A partial inventory or unsupported file is an explicit scope limitation.

Use the actual [Decompiler](https://github.com/thytabakman-jpg/Take-5/blob/main/runtime/compile_decompiler.mjs) result as the source-unit registry. Use the temporary working.consolidated view before reorganisation and working.layered plus layerByUnit/layerComparisons as suggestions; review the taxonomy and unresolved layer. One decompose invocation yields all of these; reuse it across Steps 2–5. For historical comparison, supply historical records with optional file and integer order fields from actual Git history; inspect historicResidual and historicalChanges. Use includeWorking:false if large views would duplicate expensive transfers; reconstruct from exact registry when needed. Preserve every source occurrence until its disposition is verified. Retain source locators, original ordering and exact bytes where protected.

The consolidated view is a lossless working representation, not a replacement for original source offsets. The current executable partitions the originals and produces the view in the same invocation. Treat the consolidated view as the logical input to semantic decomposition, retaining the original registry for verification. Check the complete source corpus and relevant histories; follow rename and predecessor paths where the governing scope requires it.

### Step 4: Layering

Group information by definitions, claims, evidence, inferences, mathematics, methods, architecture, historical information, unresolved questions and additional actual responsibilities. Classify each semantic unit within its structural source span; preserve attribution, qualifications and cross-layer relationships. Defer permanent section and anchor mapping until Step 8. Use temporary holding sections for unresolved information. No destructive edits yet.

For load-bearing formal research, assess symbol/object identity, types, domains and codomains, quantifier scope, composition, proof prerequisites and evidence integrity using the applicable controls in [PD integrity protocol](https://github.com/thytabakman-jpg/Reaserch/blob/main/Projects/Mathematics%20and%20Formal%20Methods/PD/protocol/PROTOCOL.md)–[Mathematical prerequisite-integrity gate](https://github.com/thytabakman-jpg/Reaserch/blob/main/Projects/Tool%20and%20System%20Research/ImprovementCore/tool-ecosystem/MATHEMATICAL_PREREQUISITE_INTEGRITY_GATE_001_2026-10-06.yaml); preserve unsupported or unresolved objects without treating them as stable mathematical primitives. These are conditional integrity controls, not permission to claim a native PDAudit run or require the historical experimental campaign.

The current executable supplies structural tags and a semantic unresolved tag, not an automatic Other category. Assign Other at the host level only for understood material outside existing categories; do not hide unknown classifications there. Every unit, including code and structural material, remains accounted for. The layer taxonomy is extensible.

### Steps 5–8: Deduplication, synthesis, architecture and assignment

Host resolves exact and semantic equivalence, subsumption, partial overlap and contradictions within layers, preserving all distinct material and source identity. Never infer semantic equivalence from similarity. Synthesize after layering; reorganize by actual responsibilities, not by original file. Preserve conflicting views as attributed positions. Historical material stays separate from current conclusions. Produce synthesised material and per-unit preservation mappings; Step 7 establishes architecture, Step 8 final file assignments and retirement decisions, and Step 9 integrates affected edits.

Remove exact redundancy only when context, provenance and responsibility are preserved. Semantic similarity is not equivalence. Distinguish equivalent material, subsumption, partial overlap, contradiction and independence; keep unresolved distinctions. Establish the authoritative home for each information type and preserve legitimately distinct navigation, operational and historical roles. Host judgments must be source-located and explicitly distinguished from computational receipts.

Review information type, scope, attribution and operational responsibilities before accepting exact or semantic reduction. Assess every transformation using the original state as baseline. For relevant dimensions d, require evidence that each protected or relevant dimension does not regress and that at least one meaningful dimension improves; this is a qualitative Pareto-improvement rule, not a global optimum or numerical certificate. Unknown evidence is OPEN, not GO. TWEAK repairs specific regressions and missed gains, then reassesses; stop at justified GO, NO-GO or a demonstrable unresolved blocker. Do not treat tentative grouping as authority. Prefer existing homes and require a justified independent responsibility for a new file. Finish architecture and final file/anchor assignments before reference transformation.

### Step 9: Dependency preparation and audit

Run Dependency with `{"mode":"prepare","before":FILES,"moves":{"owner/repo:old.md":"owner/repo:survivor.md"},"anchors":{"owner/repo:old.md#old-heading":"owner/repo:survivor.md#new-heading"}}`. Use returned `edits` as rebased original texts (keys are original sources); unchanged text comes from the frozen snapshot. Resolve OPEN mappings; retain source if ambiguous. This prevents losing relative-link context during merging. All mapped destinations must be established before coordinated repair. No writes occur in the operator.

Execute [Dependency preparation and audit](https://github.com/thytabakman-jpg/Take-5/blob/main/runtime/compile_dependencies.mjs). Build a revision-bound reference index via `{"mode":"index","before":FILES,"roots":IDS}` before discovery where needed; reuse its actual index as referenceIndex for preparation and intermediate audits with the same verified operator version. Reparse changed records and retain indexStats; keep the full frozen snapshot and run the final candidate audit without an externally supplied cache. After final destinations are chosen, prepare against the frozen originals, before integrating transformed reference spans into the candidate. Preserve relative reference context and explicitly map renamed section anchors. When a subsequent correction changes a destination or anchor, refresh the mapping, rerun affected preparation and audit, and invalidate affected receipts.

Integrate prepared references into final texts; apply coordinated changes to incoming references, indexes, inventories, registries and manifests. Run Dependency in audit mode with the same before, moves and anchors, plus `after` candidate. Resolve reported issues and explicitly inspect unchecked references. A benign retired-path literal may be dispositioned with `literalReviews:[{source,target,contentDigest,reviewed:true,rationale}]`, using the exact issue digest and source-located evidence; do not use this for an operative or dangling reference. Independently search retired paths, filenames, encoded paths, section anchors, code/config references and cross-repository links not supported by the operator. Verify actual functional dependencies and run relevant tests. Do not ignore residuals merely because the destination exists. If scope or unsupported-reference coverage cannot be established, remain OPEN.

Run [Dependency preparation and audit](https://github.com/thytabakman-jpg/Take-5/blob/main/runtime/compile_dependencies.mjs) against the exact candidate and recorded mappings. When an affected reference no longer has a distinct job, review the actual missing-edge receipt; provide relationshipReviews entries with edgeId, beforeDigest, afterDigest, mappingDigest, kind (internalise, subsumed or eliminate), reviewed:true, source-located rationale and authorization. Subsumed requires replacementTarget and replacementAnchor; eliminate requires nonoperative:true. Internalise applies only to a formerly cross-file unanchored reference now within one survivor. Never waive actual dangling links or functional dependencies. For explicitly declared JSON inventories, run C03 mode inventory with before, moves, specs (source, entriesKey, pathKey, countKey); integrate returned edits and rerun with after. Review unsupported inventories manually; distinct metadata is not redundant. Pass verified inventoryReports to C04. The operator is bounded: supported reference syntax is not the complete dependency universe. Use [Research Sorter](https://github.com/thytabakman-jpg/Reaserch/blob/main/.github/skills/research-sorter/scripts/sort_research.py)–[Knowledge Web source path resolver](https://github.com/thytabakman-jpg/Reaserch/blob/main/Tools%20and%20Workflows/Individual%20Tools/Knowledge%20Web%20Explorer/source-path-resolver.mjs) when the relevant paths, graph or relationship coverage requires them; use [Canonical Authority cross-repository validator](https://github.com/thytabakman-jpg/Reaserch/blob/main/Projects/Philosophy/Jewish%20Philosophy/tools-and-validation/tools/check_canonical_authority_cross_repo_links.py)–[Canonical Authority Markdown validator](https://github.com/thytabakman-jpg/Reaserch/blob/main/Projects/Philosophy/Jewish%20Philosophy/tools-and-validation/tools/check_canonical_authority_markdown_links.py) only for their actual Canonical Authority scope. Inspect each selected resource's current contract and prerequisites; do not treat a link in this catalogue as evidence that a tool ran. Where a dependency cannot be resolved within scope, withhold the affected retirement or publication; do not force a reference to a merely existing destination.

### Step 10: Candidate verification

Run Verifier with `before,after,decomposition,dependencyReport,history,dispositions,retire,allowedChanges,scopeReview`. The disposition map is keyed by unit ID. Exact: `{kind:"exact",target,start,end}`; semantic: same span with `kind:"semantic",reviewed:true,rationale`; historical: `{kind:"historical",reference:immutableGitHubBlobURL,reviewed:true,rationale}`; authorized removal: `{kind:"authorized-removal",reviewed:true,authorization,rationale}`. All offsets are UTF-16 code units. Unique literal spans in the same survivor or declared mapped survivor can be automatically matched; exact mechanical reference-only changes are checked against preparation output. Review these receipts for changed meaning or attribution; provide explicit dispositions where exact spans are not adequate. `scopeReview:{complete:true,evidence:"source-located coverage and functional test evidence"}` is allowed only after actual independent review of scope and unsupported references. A reported semantic review is not a proof. Maintain source provenance even for exact duplicates. Require READY_FOR_PUBLICATION plus actual semantic/functional evidence and no affected OPEN obligations.

Execute [Preservation and publication verifier](https://github.com/thytabakman-jpg/Take-5/blob/main/runtime/compile_verify.mjs) and retain its actual output. Set requireProvenance:true and sourceRevisions to independently resolved repository-to-commit mappings. Preserve the returned provenance manifest (JSON.stringify(provenance)) and digest in an authorized durable compilation record before retiring files; record the storage location. Avoid self-referential candidate digests: do not insert the generated manifest into any file in its own hashed candidate snapshot. Prepare the exact manifest as part of the guarded commit message where practical, or use a separately authorized durable ledger outside that snapshot. In a commit-message route the manifest becomes durable atomically with the commit; verify its exact bytes from the independently retrieved commit message. Do not alter the frozen branch separately to store the record. Withhold deletion if no durable route is available. During publication verification supply provenanceStorage with the independently retrieved exact text and durable reference; do not merely echo the calculated manifest. Assess candidate-specific semantic preservation, responsibility fulfilment, historical evidence and operational regressions independently of automatic exact-span matches. A computational pass does not prove semantic equivalence, authorize a mutation, or certify unscanned dependencies. Apply the scope, evidence, authority and continuation principles of [Semantic Worker Contract](https://github.com/thytabakman-jpg/Take-5/blob/main/architecture/Semantic%20Worker%20Contract.md) at the host/operator boundary; its registered-tool ABI is not required for Compile. Recheck all changed inputs before relying on a receipt.

### Step 11: Guarded publication

Recheck frozen Git revisions and source identities. Use one guarded commit per affected repository (or isolated branch and PR if branch rules require); never overwrite intervening changes. Cross-repository publication is not atomic: coordinate ordering, avoid transient broken live paths, record partial publication and recover explicitly. Only delete approved files once replacement content and dependencies are ready. In execution mode implement validated GO consolidations, including physical deletion; do not stop at a recommendation or substitute a redirect stub. If authorization, verified preservation or dependency closure is incomplete, withhold affected writes. Record commit and blob identities or the legitimate reason for no write.

### Step 12: Post-publication verification

Re-fetch each committed snapshot from the intended branch and compare exact content. Re-run verifier with `publication:{revision,baseDigest,files}` for a single verified snapshot; record per-repository commit identities for multi-repository runs. Verify retired paths are absent, surviving destinations and intended relationships are current, concurrent work is preserved, and applicable functional checks remain valid. Re-run affected dependency or preservation checks when the published state differs from the candidate. A commit alone is not completion.

### Continuation and closure

Maintain one compact execution ledger, reusing the operator outputs rather than duplicating their contents.

| Record | Minimum required evidence |
| --- | --- |
| Run | Scope, mode, target revisions, authorization, current stage |
| Stage | ID, inputs, predecessor evidence, disposition, output or blocker |
| Operator | Exact version, execution route, input/output identity, fixture evidence, actual result |
| Candidate | Retired/survivor paths, GO/NO-GO/TWEAK, source and dependency mappings, preservation evidence |
| Publication | Commits, verified state, actual deletions, residuals |
| Continuation | Last verified checkpoint, outstanding obligations, next operation, storage location if available |

Persist a recoverable checkpoint in authorized storage when needed, without creating unnecessary repository reports or inventing durable state. After a blocker, record the exact unmet requirement, recovery attempts and affected work; continue independent authorized stages or groups. Do not repeatedly ask for authorization already granted. Resume only for the same authorized scope and current revisions; invalidate stale evidence and reconcile intervening changes. Continue until applicable obligations close or an actual limit prevents further progress. Report incomplete execution explicitly, including affected retirements withheld and precise remaining work.

Completion requires actual authorized deletions, preserved information and provenance, coherent ownership, repaired dependencies within admitted scope, independently verified functional consequences, and verified publication. The three operators never independently authorize destructive edits. Their finite outputs are evidence, not a substitute for semantic or operational review. No tool count, similarity score or partial result constitutes completion.

Measure actual elapsed time, GitHub requests and bytes, repeated reads, operator comparison and index counters, host interventions, and preservation/dependency outcomes when available. Compare against a genuinely comparable prior compilation, not a fabricated baseline; PD is a simplicity reference. Report the actual before/after file counts, surviving and retired paths, semantic and dependency residuals, verified operator dispositions, tests and commit links; distinguish discovery-only, recommendations-only, verified execution, partial and blocked outcomes. For no-write modes report only the authorized deliverable, never completed physical compilation.

Do not substitute a plan for execution.

### Prompt-design rationale (non-normative)

- Khot et al. (2023), [Decomposed Prompting: A Modular Approach for Solving Complex Tasks](https://openreview.net/forum?id=_nGgzQjzaRy), ICLR: delegate specialised subtasks rather than duplicate implementation details.
- Zhou et al. (2023), [Least-to-Most Prompting Enables Complex Reasoning in Large Language Models](https://mlanthology.org/iclr/2023/zhou2023iclr-leasttomost/), ICLR: order manageable dependent subtasks.
- Liu et al. (2024), [Lost in the Middle: How Language Models Use Long Contexts](https://aclanthology.org/2024.tacl-1.9/), TACL: long-context retrieval can depend on position; foreground essential instructions and retrieve detail at use.
- Shen et al. (2024), [TaskBench: Benchmarking Large Language Models for Task Automation](https://proceedings.nips.cc/paper_files/paper/2024/hash/085185ea97db31ae6dcac7497616fd3e-Abstract-Datasets_and_Benchmarks_Track.html), NeurIPS: distinguish task decomposition, tool selection and parameter prediction.

These studies motivate the design; they do not establish the relative performance of the old and new Compile prompts. Compare on equivalent actual tasks before asserting a performance gain.
